## 1. The two leaks (both in files that are not Dev 1's; pinned as labelled KNOWN-LEAK tests that pass while the leak exists)

1. **A token in a mangled path is written to the access log.** `logPathFor` (`server/app.ts:55`) masks a path only when it still starts with the route's exact prefix. Logged raw, with the token in full: `//api/connect-links/<token>`, `/api//connect-links/<token>`, `//h/<token>`, `/h//<token>` (the head is masked, the token is not), `/API/connect-links/<token>`, `/api/Connect-Links/<token>`, `/api/connect-links%2F<token>`, `/api/connect-links;v=1/<token>`. **Reachable in production**: `API_PUBLIC_URL` passes its schema with a trailing slash (`lib/env.ts:92`, the pathname may be `/`), and the hand-over link was built as `${API_PUBLIC_URL}/h/<token>` (`token.ts:77`), so every staff hand-over link became `https://host//h/<token>` and its token was logged on use. **Fixed on our side** in commit `199f3c9` (the base loses its trailing slashes; tested first and seen failing on the old code). The leak in `logPathFor` itself is still open. Smallest fix, in `server/app.ts` (Dev 2's): finish `logPathFor` with `.replace(/[A-Za-z0-9_-]{32,}/g, (m) => (UUID.test(m) ? m : "***"))` in every branch.
2. **An unexpected error's message is logged with only `redactSecrets` applied.** `lib/errors.ts:66` (`[api] unexpected error: ...`) and `server/node.ts:116` (`[server] unexpected error: ...`). `redactSecrets` (`packages/types/src/errors.ts`) knows connection strings, JWTs, Supabase keys, Meta `EAA...` tokens and bearer headers; it does not know phone numbers, the Anthropic key, app secrets or connect-link tokens. Tested: a thrown message with a phone (the shape a unique-violation detail has) and an `sk-ant-` key is logged in full. Smallest fix: log `err.name` only in those two lines; or keep the message and add phone masking (`agent/llm/mask.ts maskPersonalData`) plus an `sk-ant-` and a 32+ key-run pattern to `redactSecrets`.

Pinned in `request-logger.test.ts` (each test says which file must change and "flip to an ordinary test when fixed"): eight mangled paths through `logPathFor`, two through a real server, four unexpected-error cases. One KNOWN LIMIT: the logger prints whatever path a client asks for, so a phone number in an address no route of ours takes is logged (no route of ours takes one).

## 4. LLM trace masking: what it covers, and what is not masked

Through the real client and the real exporter into a local server. **Capture off (the default)**: only the business id (an attribute and a tag), the conversation id, the model, tokens, cost and lengths leave; the customer's message, the reply, the system prompt, any number, and on a failed call the provider's message never do. **Capture on** (`LANGFUSE_CAPTURE_TEXT=true` exactly): message and reply text are sent, cut to 2000 characters, through `maskPersonalData`. **Every shape `mask.ts` claims is masked**: E.164, without the plus, ten digits, with the country code and spaces or dashes, with a leading zero, groups of five, three and four, a single space between every digit, a US number, and email addresses (11 shapes tested; none leaked). The system prompt (the business's name, persona, rules) is never sent. **Not masked, documented as KNOWN LIMITS (mask.ts is unchanged; the tests pass while these exist)**: a number with round brackets (`+91 (98123) 45621`), with a dot between groups, with two spaces or a space and a dash between groups, written in Tamil, Devanagari or full-width digits, or spelled out; and everything that is not a phone number or an email (names, budgets, addresses, any detail), because masking is by pattern. `mask.ts` also cuts text at 20,000 characters. Recommendation: keep capture off in production (it is the default), or, if it is turned on for debugging, accept that names and details are visible there; a better pattern for the brackets, dots, double separators and non-ASCII digits is a small change to `mask.ts` that is not made here. **Can't tell from code**: whether `LANGFUSE_CAPTURE_TEXT` is on in staging or production. One observation, not a masking leak: the exported resource carries `service.name` as `unknown_service:<path of the node executable>`, so the host's file path reaches the tracing service.

## 5. The static guard

Every `console.*` call in the backend's source (103 today) is scanned; a call that interpolates or passes something whose name says phone, token, secret, key, body, text, message, name, email, notes and so on (camelCase and snake_case read word by word; ids, an error's class name, codes, statuses and sizes are safe), or an argument that is not a string, is flagged. Dev 1's files: 3 calls are flagged and allowlisted with a one-line reason each (`takeover.ts` `Trouble.message` is a fixed label; `process-message.ts` prints an enum word and the five fixed words `answerRunThatGaveUp` returns). The guard also fails on `= console`, a destructured console, `console[...]`, `process.stdout.write` and `console.table/dir/trace`. **Flagged in other files, listed for their owners and not edited** (candidates, not proven leaks; counts per file in `static-guard-allowlist.ts`): `billing/checkout.ts` (6: an error's message after `redactSecrets`), `billing/renewals.ts` (3), `billing/start-trial.ts` (4, one prints `${text}`), `billing/trial.ts` (1, `e.message` as it is), `booking/bookings.ts` (2), `booking/google-calendar.ts` (3, Google's error text), `booking/google-sync.ts` (1), `consent/deletion.ts` (1), `conversations/mode.ts` (3, a database error's message), `notify/send.ts` (2: `err.message` after `redactSecrets` at line 176, and `notify_record`'s database message at 355), `notify/templates.ts` (1), `server/main.ts` (5: start-up lines). A NEW flagged call in those files fails the guard until it is added to the list (a fixed one never does). Not covered by the static guard: a `log(line)` callback (the request logger and the error envelope: `request-logger.test.ts`) and anything a library prints.

## 6. What is NOT proved

The real `notify.send` (the whole-turn world uses a labelled fake); Dev 2's code paths (billing, booking, notify, consent, conversations, server start-up: only the guard looks at them, and only by name); staging and production logs (and whatever Railway or Inngest add to them: Inngest prints a failed step's error itself); the real database and its error messages; the real Meta and Anthropic APIs; whether `LANGFUSE_CAPTURE_TEXT` is on in staging; the log lines `inngest/process-message.ts` writes itself (the harness mirrors its steps, not its log statements: the static guard covers them); the route error envelope inside the webhook sweep (an escaped error is caught by the test; production logs it through `lib/errors.ts`, leak 2); a phone number written in a UUID-shaped or timestamp-shaped string (the exact-form checks still catch the fixtures' own numbers).

## 7. Review

An independent review found no blocker. Fixed from it: the request logger test now waits for the line instead of a 25 ms pause; the jobs and demo sweeps assert that lines were written where one is expected; the scanner reads camelCase and snake_case names, treats `.name` as safe only on an error, ignores `//` inside a string, and the guard fails on an aliased console. Left as they are (minor, noted): the detectors share `mask.ts`'s limits (single separators), a phone inside a UUID-shaped string is hidden from the shape check (not from the exact checks), and a NEW flagged line in a Dev 2 file fails the guard until its count is raised.
