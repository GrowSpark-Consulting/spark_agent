## 1. The three routes

All three answer `not_available` (501) first while `EMBEDDED_SIGNUP_ENABLED` is off, before any sign-in check, rate limit, claim or database read (the admin route checks the flag before it looks up the caller; this is tested through the real router with a client that counts how often the database is asked for).

1. **`POST /api/admin/whatsapp/connect-link`** (platform admin), body `{ tenantId }` → 201 `{ url, expiresAt }`. `url` is `<NEXT_PUBLIC_APP_URL origin>/connect/<token>`; the token is 32 random bytes (`newConnectLinkToken`), valid 24 hours. Only the SHA-256 is inserted into `connect_links` (`created_by` is the admin's user id). **The raw token exists only in this answer**: not stored, not in the audit row (`whatsapp_connect_link.created`: business, actor, expiry), not in any log (tested). Unknown business: `not_found`; not an admin: `forbidden`; no sign-in: `unauthenticated`. Several live links per business are allowed.
2. **`GET /api/connect-links/:token`** (public, `browser: true`: the origin check, no bearer token) → 200 `{ tenantName, expiresAt }`. A malformed, unknown, used or expired token gets **one and the same** 404 `not_found` ("This link isn't valid. Ask for a new one."): the bodies are byte-identical (tested through the router, for the read and for the assisted path). A malformed token is answered without a database read. Reading does not use the link. 30 requests a minute per address (the last `x-forwarded-for` entry, the one our proxy appended), then 429 `rate_limited`; in memory, per process, so a restart or a second instance resets it.
3. **`POST /api/onboarding/whatsapp/embedded-signup` with `connectToken`** (public, any bearer token ignored): the business comes only from the link, never from the body. Order: flag, limit, token shape, the body (`validation_failed`, link untouched), the claim, the flow of PR 2 with `method: "assisted"` and `connected_by: assisted:<admin user id>`. Without a `connectToken` the route is the signed-in route of PR 2, unchanged.

## 2. Single use

1. **Claim**: one statement, `UPDATE connect_links SET used_at = :now WHERE token_hash = :h AND used_at IS NULL AND expires_at > :now RETURNING tenant_id, created_by`. Postgres runs it atomically: a second caller waits on the row lock, re-reads, sees `used_at` set and gets no row. `supabase/tests/connect_link_claim.test.sql` (in `pnpm db:test`, 35 files and 965 tests pass on a freshly reset local stack) proves the statement's conditions; a single transaction cannot race two sessions, so the lock behaviour itself is Postgres's. A unit test records the real client's calls so the three conditions cannot be dropped, and a router test sends two requests at once (one connects, one gets the neutral 404).
2. **Release**: if the flow throws, or the connection is saved with status `failed`, the claim is released (`SET used_at = NULL WHERE token_hash = :h AND used_at = :claimed_at`, so it never frees a claim someone else made), the error is passed on, and the owner can open the popup again with the same link. The link stays used only once the connection is `active`. A release that cannot be written is logged with a fixed line and does not hide the original error.
3. **After the connection is saved**: if the flow throws after the number was saved (reading it back, checking its shape) and the business now has that number `active`, the link is **not** released (a freed link would let whoever holds it connect a second number); the person sees the error and the dashboard shows the connection. The same holds when the number was already active for the business (a `conflict`): the goal is met, the link stays used.
4. **Known limit**: if the server dies between the claim and the release, the link stays used; the admin issues a new one. If an owner's connection is saved `failed` and released, the number's row exists as `failed` and is retried in place by the next attempt (PR 2).
5. A `failed` retry reuses PR 2's rules (a number already active elsewhere is `conflict`, the plan's number limit applies). `whatsapp/connected` is sent for an active assisted connection like for the other methods.
